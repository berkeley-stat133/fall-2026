Key Ideas for Today

  1. Data cleaning is a set of decisions to ensure the data meets expections given its context and intended use.
  2. Clean reproducibly: raw data is read-only; changes lives in code.
  3. Audit a data set against a checklist before analyzing.

Concept Acquisition

  1. Every cleaning step (dropping a row, recoding a label, treating -99 as missing) is a decision that changes what the analysis can conclude.
  2. Good cleaning has three parts: audit systematically, decide (and justify), and record the decision in code.
  3. The audit is a fixed checklist that can be run the same way on any data set; the decisions depend on the question being asked.
  4. “No NAs” does not mean “no missing information”: values can be disguised (sentinels, empty strings) or implicit (rows that are simply absent).
  5. Unusual values can be legitimate; impossible values are errors. Validity constraints tell them apart.

Tool Acquisition

  1. glimpse() for a first look.
  2. rename() and backticks for non-syntactic names.
  3. na_if() to convert sentinels to NA; colSums(is.na(df)) to check every column at once.
  4. tolower(), trimws(), case_when(), and if_else() for recoding.
  5. readr::parse_number() for numbers stored as text.
  6. stopifnot() to encode expectations as assertions.

Concept Application

  2. Audit a small, deliberately messy survey data frame in pairs and propose a fix for each problem.

Garbage in, garbage out

Growth in a Time of Debt

2010: Reinhart and Rogoff report that countries with government debt above 90% of GDP had average growth of -0.1%.

. . .

Widely cited in arguments for austerity policy.

2013: A grad student, Thomas Herndon, tries to replicate it from their spreadsheet and finds:

  1. A formula range that left out 5 countries
  2. Years of available data excluded
  3. An unusual weighting of countries

. . .

Corrected average growth: +2.2%.

Only one of those three was a typo. The other two were decisions.

Herndon, Ash, and Pollin (2013), “Does High Public Debt Consistently Stifle Economic Growth?” The Excel error (omitting Australia, Austria, Belgium, Canada, Denmark) got the headlines, but most of the change came from the exclusions and the weighting, which were choices about how to prepare the data.

Data Cleaning

The process of finding and handling problems in a data set, such as bad names, wrong types, missing or invalid values, inconsistent categories, and duplicates, so that it faithfully represents what was measured and permits a valid analysis.

Every fix is a choice:

  • Drop this row, or keep it?
  • Is "UCB" the same as "Berkeley"?
  • What is meant by 0?

Cleaning decisions change what your analysis can conclude, so they deserve the same care as the analysis itself.

Data Cleaning: three phases

1. Audit

Check the data against a fixed checklist, the same one every time.

2. Decide

For each problem, choose a fix and a reason. The reason depends on your question.

3. Record

Write the fix in code, with the reason, so anyone can rerun it.

The audit is systematic enough that anyone, or anything, could follow it, but the decisions are made by the analyst

Plant this idea now: the checklist is mechanical, but choosing what to do is judgment. It comes back later in the course when we use tools that automate the audit (Posit Assitant Data Cleaning mode)

3. Recording Reproducibly

  1. Never edit the raw file. No hand edits in Excel.
  2. Clean in code, in a script or .qmd.
  3. Document each decision in comments or prose.
  4. Check before and after each step: row counts, summaries.

1. Audit

The Checklist

For each of the following, you must investigate, decide, then record.

  1. Source: data dictionary, unit of observation
  2. Names: syntactic and consistent?
  3. Types: does each type match its meaning?
  4. Missing values: explicit and disguised
  1. Distinct values: inconsistent categories?
  2. Ranges and outliers: impossible or just unusual?
  3. Duplicates and keys
  4. Structure: is it tidy?

Common type problems:

  • numbers stored as text: "1,200", "$5"
  • dates stored as text
  • IDs stored as numbers (zip codes lose leading zeros: 02134 → 2134)

When types go wrong

Excel automatically converts some text into dates.

Gene In Excel
SEPT2 2-Sep
MARCH1 1-Mar
  • 2016: about 1 in 5 genomics papers with Excel gene lists had names mangled into dates.
  • 2020: geneticists renamed the genes (SEPTIN2, MARCHF1).

Another argument for keeping raw data read-only and doing all changes in code.

Ziemann, Eren, and El-Osta (2016), Genome Biology. The HUGO Gene Nomenclature Committee renamed 27 genes in 2020 partly for this reason.

Missing without NA

Implicit Missing Value

A value that is missing because its whole row is absent from the data, rather than recorded as NA.

Disguised Missing Value

A missing value recorded as a regular-looking value, such as -99, 999, "", "N/A", or "unknown". Also called a sentinel value.

Check the data dictionary: it often lists the codes used for “missing.”

Disguised missing values

age <- c(19, 21, -99, 20, 22)
mean(age)
[1] -3.4

Disguised missing values

age <- c(19, 21, -99, 20, 22)

[1] -3.4

na_if()

Replaces every element of a vector that equals a given value with NA.

age <- na_if(age, -99)
age
[1] 19 21 NA 20 22
mean(age, na.rm = TRUE)
[1] 20.5

Why is it missing?

Before you drop, keep, or fill in missing values, ask whether missingness is related to anything.

Unrelated: a survey page failed to load for a random 5% of people.

→ Dropping those rows loses precision but not much else.

Related: people with the highest incomes are the most likely to skip the income question.

→ Dropping them makes everyone look poorer.

Your options: drop the rows, keep the NAs, or fill in (impute) a value. Whichever you choose, write down why.

Recoding messy labels

case_when()

A vectorized, multi-branch if-else: returns the value paired with the first condition that is TRUE, and .default otherwise.

campus <- c("berkeley", "berkeley", "berkeley", "ucb", "laney")
case_when(
  campus == "ucb" ~ "berkeley",
  .default = campus)
[1] "berkeley" "berkeley" "berkeley" "berkeley" "laney"

For just two branches, if_else() is dplyr’s stricter version of ifelse(). More powerful string tools (stringr) are coming in Lecture 19.

Outlier

A value far from the bulk of the data. It may be correct.

Data Error

A value that cannot be true given what the variable measures.

Tell them apart with validity constraints: rules the data must follow.

  • ages ≥ 0 and below about 120; percentages in [0, 100]
  • quarters in 1–4; dates not in the future
  • across columns: end date after start date, subtotal ≤ total

Fix or remove errors. Keep outliers, and think about how they affect your summaries.

stopifnot()

Throws an error unless every condition given to it is TRUE.

stopifnot(
  all(zev$quarter %in% 1:4),
  all(zev$n_vehicles >= 1),
  all(zev$year <= 2026)
)
stopifnot(all(zev$year >= 2010))
Error:
! all(zev$year >= 2010) is not TRUE

When the data are updated next quarter, a broken expectation fails loudly.

A data frame where each variable is a column, each observation is a row, and each value is a cell.

Decide, Record, Re-check

zev_raw <- read_excel("data/raw/New_ZEV_Sales_Last_updated_07-17-2026_ada.xlsx",
                      sheet = "County")

zev <- zev_raw |>
  # Snake-case names so no backticks are needed
  rename(year = `Data Year`, quarter = Quarter, county = COUNTY,
         fuel_type = FUEL_TYPE, make = MAKE, model = MODEL,
         n_vehicles = `Number of Vehicles`) |>
  # Keep out-of-state registrations but flag them: needed for statewide
  # totals, excluded from county-level comparisons
  mutate(in_state = county != "Out Of State")
  # Note: zero counts are implicit (no row), not NA

# Nothing dropped; expectations still hold
stopifnot(
  nrow(zev) == nrow(zev_raw),
  all(zev$quarter %in% 1:4),
  all(zev$n_vehicles >= 1)
)

Cleaning is iterative: EDA will turn up new problems, and you’ll return to cleaning.

Guess the Metaphor

Data cleaning is like a tax audit: you go through a checklist to see if the data (the tax return) conforms to standards and expectations. Where it doesn’t, you decide what to change to make it conform and record those changes.

Key Ideas for Today

  1. Data cleaning is a series of analytic decisions, not busywork.
  2. Clean reproducibly: raw data is read-only and every change lives in code.
  3. Audit a new data set against a checklist before analyzing it.
  4. A disguised missing value like -99 or "N/A" hides in plain sight.
  5. An outlier is not necessarily an error: check validity before you “fix” it.
